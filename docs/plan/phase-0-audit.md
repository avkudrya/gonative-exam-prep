## Задачи

- [ ] **P0.1 GoNative (A, G).** Видимость серверных списков в mobile и web; метка источника у списка;
  переводы слов паков IELTS на ru/uk для всех уровней; академические темы в `glossaries` и
  `lexical_clusters`; свои слова (`DictionaryCustom`) для сгенерированных выражений; лимит слов
  и Premium (ADR-002).
- [ ] **P0.2 Edu / WG (B, H).** Список тем en и соответствие навыкам; правила выдачи заданий
  (servable, права, CEFR); фасад «задания по теме»; пригодность `Edu\Bench` для эссе; предложение
  `AnswerChecker`.
- [ ] **P0.3 Официальные требования IELTS (D).** Сверить по ielts.org: структура Writing Academic
  и General Training, время, минимум слов, критерии и публичные дескрипторы (текущая версия),
  вес Task 2, округление, различия Task 1 (Academic / GT). Итог — `verified`-версия конфигурации
  с источниками и датой.
- [ ] **P0.4 Эталонные данные (E).** Найти легально используемые эссе с оценками экзаменаторов
  (официальные примеры ielts.org и British Council / IDP, материалы Cambridge, открытые датасеты);
  для каждого — лицензия и что разрешено (хранить, оценивать, цитировать). Без копирования в репо,
  пока лицензия не подтверждена.
- [ ] **P0.5 Авторизация и BFF (C).** Что из `web/src/server/*` и auth-потока WG переносится
  1:1 (отдельный домен, своя cookie, CSRF).
- [ ] **P0.6 Оплата и взаимодействие продуктов (ADR-002, M).** Разовые покупки в вебхуке Paddle;
  третий продукт в `billing_products`; квоты по образцу WG. Модель «подписка Exams снимает нужные
  лимиты GoNative на свой срок»: список лимитов, единая серверная проверка доступа, признак для
  клиентов (mobile и gonativeweb), окончание, семья, возвраты, аналитика (ADR-002, пп. 1–6).
- [ ] **P0.7 Приватность (I).** Политики хранения данных у Anthropic и OpenAI для API; срок хранения
  эссе; удаление аккаунта (`DeletedAccountPurger`); что добавить в Privacy Policy gonativeweb.
- [ ] **P0.8 Документы D–N** и согласование gate с владельцем.

## Набросок плана бенчмарка (E)

Цель Фазы 1 — ответить на вопрос «насколько можно доверять разбору и числам», а не построить продукт.

**Наборы данных** (dev и test разделены, промпты не настраиваем на test):

1. **Эталон экзаменаторов** — публичные эссе с оценками по критериям (P0.4). Ожидаем десятки, не сотни:
   этого хватит для оценки грубой ошибки, но не для точной калибровки. Ограничение фиксируем явно (ТЗ §9.4).
2. **Вставленные ошибки** — свои тексты (написанные нами или моделью и вычитанные), в которые
   детерминированно вставлены известные ошибки (артикли, времена, согласование, коллокации). Здесь
   ground truth известен точно: меряем полноту и точность находок, ложные исправления и корректность
   цитат без экзаменаторов.
3. **Граничные случаи** — не по теме, короче минимума, заученный шаблон, смешение языков, инструкция
   модели внутри эссе, необычный, но корректный стиль (ТЗ §24.2).
4. **Стабильность** — те же эссе по 3–5 раз: разброс диапазонов и находок.

**Сравниваем:** 2–3 модели (Anthropic, OpenAI, xAI — ключи уже есть в MultiAdmin); один проход против
отдельных проходов по критериям; с независимым валидатором другого вендора и без; с дескрипторами
в промпте и без.

**Метрики (ТЗ §9.3):** MAE и доля в пределах 0.5 / 1.0 полосы по критериям (только на наборе 1);
полнота и точность находок, ложные исправления (набор 2); неподтверждённые утверждения (цитата не
совпадает, ссылка на несуществующее); разброс между повторами; задержка; стоимость за оценку
по `ai_usage_events`.

**Где код:** в MultiAdmin (`Exam\Bench` поверх `Edu\Ai`), после gate Фазы 0. Здесь — манифесты
датасетов, конфиги прогонов и отчёты (`benchmarks/`).
