## 2. Порядок

Решение 2026-11-23: P2.1 → P2.3 → P2.4 → P2.5 → P2.2 → P2.6 → P2.9 → P2.7 → P2.8.

**Предлагаю изменение** (вопрос 3): разделить P2.2 и поднять права и квоты перед API.

**P2.1 → P2.3 → P2.2a → P2.4 → P2.5 → P2.6 → P2.2b + P2.9 → P2.7 → P2.8**

- **P2.2a** — права, планы, квота Exams, именованные лимитеры, закрытие продукта, аудитория.
- **P2.2b** — общий purger вместе с удалением данных Exams (P2.9).

Почему так. Отправка эссе на оценку (P2.4) и запуск джоба (P2.5) — это и есть точка допуска по квоте и
правам. Если сделать квоты после них, отправку придётся писать дважды, а API между P2.4 и P2.2 будет
без лимитов. Purger логично делать вместе с тестом удаления: P2.9 его и проверяет.

Везде одинаково:

### P2.5. Джоб оценки (M)

**Компоненты:**
- `app/Jobs/Exam/AssessAttemptJob`: соединение и очередь `exam` (database, `after_commit`), `tries = 1`, в задании только ID.
- `Exam/Assessment/AttemptAssessment`: старт, выполнение, статус, отмена.
- `Exam/Assessment/ResultMapper`: результат `EssayAssessor` → контракт `assessmentResult` v1.
  - `summary` ← `reason`;
  - `findingIds` по критерию;
  - 3–5 главных исправлений по серьёзности.

**Прогон:**
- `edu_generation_runs` с `purpose = exam_assessment`, `subject = ex_attempt`;
- в `request` записаны продукт, пайплайн `p1`, руководство (ссылка и SHA), рубрика, маршрут и версия промпта;
- новая версия пайплайна — новая строка `ex_assessments`, история не переписывается (ADR-003 п. 6).

**Модель:**
- в `config/exam.php` отдельный продуктовый маршрут: `claude-sonnet-5-5`, P1, руководство v2, `exam-p1-1`, без проверки находок;
- ограничители включает код (`LimiterTriggers`);
- маршруты бенчмарка не меняются.

**Деньги:**
- только `MeteredLlm::forProduct('exam')`, строгий `ReservedRunBudget`;
- потолок $0.25 на оценку;
- неясный исход вызова → `partial` без повторов;
- фактическая стоимость → `ex_assessments.cost_usd` и `ex_usage_periods`.

**Правила без AI:**
- ≤ 20 слов → Band 1;
- другой язык → Band 0;
- оба случая — без платного вызова (K §3.3).

**Скорость.** По умолчанию 4 вызова критериев идут последовательно, около 30–35 с. Если нужно около 10 с,
есть вариант: 4 дочерних прогона под общим бюджетом родителя, как у WG. Цена та же, но понадобится больше воркеров.

**Эксплуатация:**
- шаблон supervisor `laravel-exam`;
- команда `exam:queue-health`;
- проверка в `deploy.sh` за флагом `EXAM_ASSESSMENT_ENABLED` (по умолчанию `false`; в production — только при деплое по «да»).

**Тесты** (`tests/Feature/Exam/AssessmentJobTest`, фейковый клиент):

### P2.6. Навыки, официальные результаты, жалобы (S)

- **Навыки.** После оценки находки превращаются в `ex_skill_observations` (вес по серьёзности), затем пересчитывается `ex_skill_states`: частота на 100 слов, тренд и уверенность. Удаление попытки удаляет её наблюдения и пересчитывает состояние. API: `GET skills` — частые ошибки и тренд по критериям в виде диапазонов.
- **Официальные результаты** (ADR-003):
  - `GET/POST/PUT/DELETE reported-results`;
  - согласие на калибровку отдельное и отзываемое, с `consent_changed_at`;
  - проверка по шкалам версии экзамена (PHP-порт `checkReportedResult`);
  - `GET reported-results/{id}/comparison` — «ваш прогноз и реальный результат» по последним попыткам до даты экзамена.
- **Жалобы.** `POST attempts/{uuid}/reports`: вид, сообщение до 1000 символов, лимитер `exams-report`.
- **Тесты:**
  - пересчёт навыков;
  - удаление;
  - согласие и его отзыв;
  - значение не на шкале → 422;
  - чужая попытка → 404.

### P2.2b + P2.9. Удаление данных (S)

| Блок | Что меняется | Чем проверяем, что WG не сломан |
|---|---|---|
| Аккаунты, токены (P2.1) | Код уезжает в `Products/*`, WG — обёртки | Наборы §1 без правок; паритет конфигурации; маршруты WG не менялись |
